Daily Progress Approval Cycle & Site Governance PRD

Strict approval gating, multi-channel photo audit trails, zero unapproved progress leakage into project S-Curves/EVM, and high-velocity multi-zone filtering for large construction sites.

🎯 What
A closed-loop, deterministic approval workflow governing daily site progress submissions, enforcing mandatory photo evidence, line-item BOQ rate freezing, and fast-grid zone/discipline filtering.
👥 Who
Site Engineers (rapid execution logging), Planning Engineers (gatekeepers of truth & schedule alignment), and Project Directors / Commercial Teams (financial certificates & S-Curve integrity).
⚡ Why Now
Unapproved preliminary site estimates leaked directly into project SPI/CPI and S-Curves, generating phantom progress, premature contractor billing claims, and unprovable inspections upon consultant audits.
01. Root Cause & Context

Problem Statement: The Site Progress Governance Gap

Analysis of commercial exposure, phantom EVM metrics, and site scale bottlenecks.

In large-scale contracting projects across Egypt and the MENA region, site progress reporting suffers from a systemic disconnect between field execution and planning controls. Previously, site engineers logged daily estimates that immediately influenced task completion percentages (progress_pct) without formal verification. This lack of a strict approval firewall introduced four critical failure modes:

⚠️ 1. Phantom Progress & S-Curve Corruption
Unreviewed draft reports artificially elevated project Earned Value (EV) and Schedule Performance Index (SPI). When consultant inspections later rejected the executed work, project managers faced catastrophic downward revisions on executive dashboards.
💸 2. Premature Subcontractor Billing Exposure
Commercial engineers generated Interim Payment Certificates (IPCs) relying on unapproved site figures. Discrepancies led to severe cash-flow disputes, overpayment to subcontractors, and painful financial clawbacks during owner audits.
📷 3. Photo Disconnect & Lost Evidence Trails
Site inspection photos were communicated through fragmented chat apps (WhatsApp) rather than atomic database attachments. Consequently, when Work Inspection Requests (WIRs) were audited, crucial time-stamped proof was irrecoverable.
⏱️ 4. Multi-Zone Site Cognitive Overload
On sites featuring 20+ buildings and hundreds of active tasks, site engineers were forced to scroll through monolithic tables without zone or discipline filters, leading to data entry abandonment and delayed shift closures.

02. Boundaries & Deliverables

Goals & Non-Goals

Clear boundaries delineating immediate scope from deferred integrations.

✅ Core Goals
  • ✓
    Zero-Leakage KPI Governance: Ensure calculateTaskProgress strictly aggregates only approved and partially_approved reports. Unapproved or rejected quantities never increment pm_site_tasks.progress_pct.
  • ✓
    Strict Approval Gating via RPC: Enforce state transitions through rpc_daily_report_transition, requiring Planning Engineer / PM credentials and mandatory justification reasons on rejection or reopening.
  • ✓
    Immutable Photo Audit Storage: Stream site photos directly to Supabase Storage bucket progress-photos with project-namespaced paths and foreign-key linked records in pm_daily_progress_photos.
  • ✓
    High-Speed Grid Zone & Discipline Filtering: Equip SiteWorkspaceFastGrid.tsx with instant dropdown filtering powered by classifyActivity to handle 1,000+ tasks in under 100ms.
  • ✓
    Deterministic E2E Playwright Verification: Prove end-to-end reliability via automated tests (site_engineer.spec.ts and planning_engineer.spec.ts) without facade mocks.
⛔ Non-Goals (Out of Scope)
  • ✕
    Consultant Submittal Direct Workflow: External consultant inspections (WIR Code A/B/C/D) remain managed within the Technical Office Deliverables portal. This PRD focuses exclusively on internal Contractor governance.
  • ✕
    Automatic Schedule Date Shifting: Approving daily progress updates completion percentages but does NOT automatically alter Primavera P6 predecessor logic or push activity finish dates (governed separately by Schedule Compression 001).
  • ✕
    Subcontractor Direct Payment Clearance: While cumulative quantities are updated, automated disbursement of subcontractor payments belongs to the Subcontractor IPC module.
  • ✕
    Native Mobile Binaries: Focus remains strictly on responsive PWA and desktop high-density browsers; standalone iOS/Android App Store distribution is out of scope.

Persona: Eng. Tarek (Planning Engineer)

As a Planning Engineer encountering an exaggerated site quantity,

I want to reject the report while providing a mandatory Arabic justification,

So that the report returns to the site engineer for correction without polluting project KPIs or locking previous quantities.

Acceptance Criteria
  • Rejecting requires a non-empty text justification; empty submissions are blocked client and server side.
  • Rejection executes via rpc_daily_report_transition(p_report_id, 'reject', p_reason).
  • Rejected reports are completely excluded by calculateTaskProgress and getCumulativeQtyByTask.
  • The task's progress_pct stays unchanged, and the Site Engineer's previousQty remains clean.

2. Database RPC Contract: rpc_daily_report_transition

Migration 038 implements a transactional state machine function strictly enforcing role authorization, transition legitimacy, rate snapshots, and allocation suspension:

PostgreSQL PL/pgSQL Function Signature & Execution Gate supabase/migrations/038_daily_report_transition_rpc.sql 
CREATE OR REPLACE FUNCTION public.rpc_daily_report_transition(
  p_report_id UUID,
  p_action TEXT,            -- 'submit' | 'approve' | 'reject' | 'reopen'
  p_reason TEXT DEFAULT NULL  -- Mandatory for 'reject' and 'reopen'
) RETURNS JSONB AS $$
BEGIN
  -- 1. Role Verification
  -- 'submit': Submitter or Project Manager
  -- 'approve' / 'reject': Planning Engineer, Planning Manager, PM, or Admin
  -- 'reopen': Planning Engineer or Admin

  -- 2. State Validations
  -- 'submit' requires from_state IN ('draft', 'rejected')
  -- 'approve' requires from_state = 'submitted'
  -- 'reject' requires from_state = 'submitted' AND p_reason IS NOT NULL
  -- 'reopen' requires from_state = 'approved' AND p_reason IS NOT NULL

  -- 3. Auto-Actions on 'approve':
  -- Freezes BOQ snapshot rate & revision on all lines:
  UPDATE public.pm_daily_progress_lines l
  SET
    line_status = 'approved',
    line_reviewed_by = v_actor_user_id,
    line_reviewed_at = now(),
    snapshot_rate_egp = COALESCE(l.snapshot_rate_egp, (
      SELECT b.rate_egp FROM public.pm_boq_items b WHERE b.id = l.boq_item_id
    )),
    source_boq_revision = COALESCE(l.source_boq_revision, (
      SELECT b.revision FROM public.pm_boq_items b WHERE b.id = l.boq_item_id
    )),
    updated_at = now()
  WHERE l.daily_progress_id = p_report_id AND l.line_status = 'pending';

  RETURN jsonb_build_object('success', true, 'to_state', v_to_state);
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

3. Supabase Storage Architecture: progress-photos Bucket

Site photos represent non-repudiation audit evidence and are governed by strict upload pipelines:

Component Specification Detail Operational Rationale
Storage Bucket progress-photos (Public read with signed upload token) Isolates high-volume binary multimedia from database transaction logs.
Path Topology {projectId}/{reportId}_{timestamp}_{idx}_{sanitizedFilename}.{ext} Enforces project multitenancy partitioning and prevents file overwrite collisions.
Payload Limits Max 10 MB per image; supported MIME: image/jpeg, image/png, image/webp Guarantees low mobile data usage for field site engineers over cellular networks.
Memory Guard Client sets tracked via objectUrlsRef = useRef<Set<string>> with URL.revokeObjectURL() Prevents browser memory bloat and tab crashes on low-spec site tablets.

4. Mathematical Governance & Earned Value Proof

In accordance with enterprise project controls, official task progress is computed exclusively from approved daily progress reports, weighted by contractual BOQ monetary rates:

P_task = [ Σ ( min( CumulativeQty_i / ContractQty_i, 1.0 ) × (ContractQty_i × Rate_i) ) ] / [ Σ (ContractQty_i × Rate_i) ] × 100%
Where: i ∈ Approved BOQ Line Items belonging to Reports where Status ∈ {'approved', 'partially_approved'}.

Exclusion Invariant: If a report is in state 'draft', 'submitted', or 'rejected', its qty_today contributes 0.00 to the task progress numerator and denominator.

08. Architectural Governance

Open Questions & Risk Mitigations

Key architectural trade-offs resolved with assigned ownership.

Q1: Offline Sync & Poor Site Cellular Reception?
Resolution: The Wizard queues attachments in local IndexedDB via Zustand offline storage. Once connectivity is restored, background workers upload photos sequentially with retry exponential backoff.
👤 Assignee: Mobile Offline Lead (Zustand)
Q2: Unintended BOQ Price Leakage to Site Subcontractors?
Resolution: The <PriceGate> component and canViewPrices(roles) guard completely strip rate_egp and monetary sums from UI rendering for site engineers and subcontractors.
👤 Assignee: Security & RBAC Architect
Q3: Partial Line Approval vs Full Report Rejection?
Resolution: If only 1 out of 5 lines is rejected, Planning Engineers can reject the single line via rejectDailyReportLine, transitioning the report to 'partially_approved' while preserving valid progress.
👤 Assignee: Planning Controls Lead
Q4: Historical Report Modification Audit Trails?
Resolution: Reopening an approved report requires 'reopen' action in rpc_daily_report_transition, which suspends active allocations and records an append-only audit event in pm_task_events.
👤 Assignee: Database Governance Team
